# 共用記憶（memory/）

所有 agent（Claude Code、Codex、派工子 session、雲端 thread）**只透過這個資料夾溝通**。不靠對話交接：要交給別的 agent 的事，一律寫進 `handoff.md` 或對應欄位檔。
記憶不是逐日敘述，而是固定欄位的條目。架構照 jev-hearthstone 的 `memory/`，源自 AutoTavern 論文（arXiv 2610.33845 §4、附錄 A）的 typed research memory（S-001）。

2026-10-28 建立時，從 README「踩過的坑／已知限制」、`reports/status/status.md`、git log（`8d18901`…`560ddcc`）、`reports/ovr-inseason-2026-27/v5/pathA/` 與 Claude 的 auto-memory 搬入初始條目。逐份報告仍在 `reports/`，條目只寫結論並指向報告。

## 開工必讀順序

1. `handoff.md`（現在在做什麼、下一步）
2. `digest.md`（先跑 `python memory/build_digest.py`；lessons 不要再犯的錯＋rulings 使用者裁定的摘要；要看發生什麼、理由，`grep -n '^### L-012' lessons.md` 查全文）
4. 其餘按需查：`grep -n "關鍵字" memory/findings.md memory/experiments.md memory/references.md`

## 寫入規則

- **只追加新 ID**：新條目接在檔尾，ID 取該檔目前最大號 +1。不重編號、不刪條目。
  - 例外：使用者要求整併時（rulings、lessons 2026-10-30），同主題併成一條、過時的刪掉，舊 ID 一律列進檔尾「舊 ID 對照」表（舊 ID → 新條目或「刪除」），引用不會斷；pre-commit 把表裡的 ID 算保留。之後同主題的新裁決改寫該主題條目，並在「合併」欄記新 ID。
- **一筆一件事**：一個發現、一次實驗、一條裁決、一個教訓各一筆；彼此用「相關」欄位互指（例如 `F-012、E-034`）。
- **狀態改變時改原條目**：只改「狀態」欄，括號註明日期與原因，例如 `被推翻（2026-11-02，E-040 重跑後 ρ 0.41）`；同時寫一筆新條目說明新證據，兩筆互指。
- **數字照量到的寫**：證據欄寫指令、檔案路徑與數字；沒量過的寫「待驗」，不要寫成已證實。
- **樣本內不算證據**：卡片若用 RAPM 做 align／封頂／混合目標，它對 RAPM 的 ρ 只能寫「樣本內」，不能當驗證（R-007）。
- **抓到錯誤就寫 lesson**：每個被抓到的錯誤（使用者指出的、測試抓到的、自己發現的）寫成一筆 lesson；能自動檢查的就加測試，把測試檔或 npm 指令寫進「對應測試或關卡」。
- **收工**：新發現、實驗、裁決、教訓各寫進對應檔，然後**覆寫** `handoff.md`。模型或卡片輸出有變時，另照 L-021 重產審查表。
- **commit 檢查**：`.githooks/pre-commit`（新 clone 先跑 `git config core.hooksPath .githooks`）會擋兩件事：改到 `src/`、`scripts/`、`test/` 或條目檔卻沒一起改 `handoff.md`（確定不需要時 `HANDOFF_OK=1 git commit`）；條目 ID 重複或刪掉既有 ID。
- 欄位定義與範例寫在各檔檔頭。
- 「來源」欄：commit、報告路徑或對話日期；沒有就省略。

## 版本號

四條軌道各自編號：`card`（卡片 OVR）、`inseason`（賽中 OVR）、`defense`（防守）、`sim`（模擬引擎）。格式 `0.MINOR.PATCH`，接進正式對局（F-010）才發 1.0。

| 情況 | 寫法 | 例 |
|---|---|---|
| 實驗（還沒採用） | 基準版本＋`+E編號` | `card 0.1.0+E055` |
| 實驗採用，且樣本外更準（OVR）或球隊 MAE 進步 | 升 MINOR，PATCH 歸零 | `card 0.2.0` |
| 實驗採用但沒有變準，改了公式或參數且影響大 | 升 PATCH（批次發版） | `card 0.1.1` |
| 小版本：修 bug、修資料抓錯，或影響小的公式／參數改動（R-064） | 加字母後綴 | `card 0.2.6a` |
| 只更新比賽資料 | 版號不變，只換「數據截至」日期（R-063） | `inseason 0.2.5`，數據截至 11/02 |

- `inseason` 版號＝它用的先驗 `card` 版號（R-050）：先驗 card 0.2.4 → inseason 0.2.4；只換比賽資料版號不變（R-063），新賽季自己的模型改動寫 `0.2.4-s1`。
- 實驗不佔版號：失敗的只留 E 條目。平行實驗都掛在同一個基準上（`0.1.0+E055`、`0.1.0+E056`），不會假裝彼此有先後。
- 多個實驗一起採用時合成一版，在 R 條目寫明「0.2.0 = 0.1.0 + E-054 + E-055」。
- 新報告目錄用 `reports/<軌道>-<基準>+E<編號>-<短名>/`；舊目錄（`ovr-v58…` 等）不改名，對照見 R-018。

### 各位數什麼時候升

判斷問題：這次改動有沒有讓模型更準？（R-019）

| 位數 | 升的條件 | 例 |
|---|---|---|
| MAJOR | 對局依賴的介面改了，舊存檔、卡組、對照表會失效；1.0 前固定 0 | 0→1：卡片接進對局（F-010）；1→2：屬性欄位改名或刪除 |
| MINOR | 卡片／賽中 OVR 在樣本外更準（2K27 ρ、RAPM 分半、沒看過的季；樣本內 RAPM 擬合不算，R-007），或球隊端 winsMAE 進步 | 新方法讓 2K27 ρ 與分半 RAPM ρ 都上升 |
| PATCH | 沒有變準，刻意改了公式或參數（含重擬合），而且影響大 | drive 拆成 foulDraw＋新 drive；拉回目標改成本人歷史 |
| 字母（小版本） | 修 bug、修資料抓錯，或影響小的公式／參數改動（R-064） | 0.2.6 → 0.2.6a |
| 不升 | 輸出完全沒變，或只更新比賽資料 | 重構、註解、報告排版；每日賽中更新 |

- 「影響小」＝三條都成立：前 20 名換 ≤ 2 人、前 300 名移動 ≥ 10 名的 ≤ 30 人、evaluate.mjs 通過的門檻數沒減少（R-064）。有一條不成立就是影響大。字母用到 z 就升 PATCH。
- patch note 同一基底版號的字母版合寫一段（「0.2.6a–c」）。
- 1.0 前新增或拆分屬性本身不決定位數，看有沒有變準（還沒有遊戲端依賴欄位）。
- 不採用里程表式進位：0.1.9 之後是 0.1.10。上一位升了，下面歸零（含字母）。
- 一次發版只升一位，取影響最大的那個。
- 升 MINOR 要過 G1–G5；升 PATCH 過 G1–G3 即可，但若前 20 名換掉超過 3 人，要重跑 G4。
- 批次發版：驗收通過的實驗先排隊，使用者 G5 抽查後合成一版。預期 MINOR 約一批研究一版（1–2 週），數字長太快通常是把實驗當成發版。
- 跨軌道各自升版，相依寫在 R 條目，例如「card ≥ 0.3 需要 sim ≥ 0.2」。

## 五道門

一個結果沒過它該過的門，就不寫成「已證實」。

| 門 | 內容 | 怎麼檢查 |
|---|---|---|
| G1 構建 | 改動後測試全綠 | `npm test`；改到特定批次時加跑對應的 `npm run test:<批次>`（例如 `test:ability-eighth-c`） |
| G2 契約 | 每張卡、每個模擬板都記得它用的模擬版本、RAPM 季窗與資料來源（含 stint 來源與 sha256） | 報告或 json 寫明版本與來源雜湊；來源不一致就不能拿來比（F-021、L-018） |
| G3 比較 | 只在同一模擬版本、同一人群（例如 pooledPoss ≥ 5000）、同一組 seed 下比較；隨機性要用球隊＋seed 重抽區間 | 報告寫明人群門檻、seed 數與區間算法 |
| G4 樣本外 | 參數在已看過的資料上選；交付前在沒參與挑選的資料上再測一次（RAPM 分半 A→B／B→A、沒看過的季、預註冊凍結後才看的起點） | 預註冊檔先凍結（附 sha256）再看答案；讀 RAPM 的卡不拿 ρRAPM 當證據 |
| G5 現實 | 使用者抽查：熟悉球員的名次、前十長人組成、2K27 或 RAPM 其一對得上；賽中 OVR 對真實賽季 | 審查表（`reports/status/`）＋球員抽查表（R-003、R-004） |

## 角色

照 AutoTavern 的分工，派工時 task 開頭寫「用 role-xxx skill」（`.claude/skills/role-*/SKILL.md`）；不是 Claude 的 agent 直接讀那份 SKILL.md。角色之間只透過這個資料夾交接。

| 角色 | 負責 |
|---|---|
| `role-lead` | 讀 handoff 挑下一個問題、寫 spec、審結果、收工寫 memory。不自己實作。 |
| `role-model` | 模擬引擎與數值模型（`src/`、possession、防守、球權）。 |
| `role-card` | 卡片 OVR、屬性建構、賽中 OVR。 |
| `role-audit` | 樣本外驗證、回測、審查表；必須和產生該結果的 session 不同。 |
