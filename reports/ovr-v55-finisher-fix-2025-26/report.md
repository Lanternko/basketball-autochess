| 任務的歸因 | 核對結果 |
|---|---|
| `usageFromEv`（`src/probability_model.js`）用期望得分 softmax 分配出手，命中率越高拿到越多球 | **不成立（死碼）**。v41 之後的 `creationPlan` 用實測的每分鐘機會率搭配與球員屬性無關的 `elasticLineup` 次方重新正規化來分配出手，`usageFromEv` 在 v53 引擎的路徑上沒有被呼叫，所以沒有「效率→球量」的回饋迴圈。 |

## 1. 資料：餵球／自主出手的分割

repo 內**沒有** tracking 的 touches/drives/potential-assists，也沒有「被助攻的出手數」——
NBA play-by-play 只在命中的球上記助攻。因此採兩階段硬分割（`prepare-origin.mjs`）：先用聯盟
層級算出每個 (區域, `descriptor`, `subType`) 類別的命中球被助攻比例 q_k，再把 q_k > 0.5 的
**整個類別**判為餵球、其餘判為自主。每球的歸屬只看動作類型、不看進不進，所以兩邊命中率是直接
觀測、沒有「只看命中球」的抽樣偏誤；補籃／撥籃另計並剔除。

分割結果（`shot-origin.json`，四季齊全）：

| 季 | 區 | fed 出手 | fed FG% | self 出手 | self FG% | 差 | fed 占比 |
|---|---|---:|---:|---:|---:|---:|---:|
| 2025-26 | short | 42395 | .681 | 54012 | .492 | **+.189** | .440 |
| 2024-25 | short | 43620 | .666 | 52477 | .488 | **+.178** | .454 |
| 2023-24 | short | 44170 | .651 | 54292 | .505 | **+.146** | .449 |
| 2022-23 | short | 43218 | .662 | 55072 | .505 | **+.157** | .440 |
| 2025-26 | long | 70350 | .368 | 20391 | .331 | +.038 | .775 |
| 2025-26 | mid | 4991 | .415 | 16577 | .417 | −.003 | .231 |

**這是禁區現象**：三分差 .038、中距離差 ≈ 0，所以 B1 只作用在 `short` 區（資料決定的範圍，
不是事後縮小）。

球員層（2025-26、非補籃禁區出手 ≥40 的 417 人）：d_i = fedFG% − selfFG% 的 attempt-weighted
平均 d̄ = .1852、觀測變異 .012578、平均抽樣變異 .011138 ⇒ **τ² = .001440**。τ² 這麼小代表
d_i 的球員間離散幾乎全是抽樣雜訊，餵球溢價是**聯盟層級的結構效應，不是球員技能**，所以 EB 會
把 D̃_i 幾乎全收到 d̄。真正的判別變數是 **s̃_i**（Karlo .821、Jaxson Hayes .879、Gobert .850
vs Dončić .138、Harden .127），它離散大且量測精確。

## 2. 設計與實作

```
adj_i(assist) = D̃_i * ( [這球用了接球投機率] − s̃_i ) + c      # 只作用在 short，補籃為 0
s̃_i = (fedA_i + 25·s̄) / (A_i + 25)
D̃_i = d̄ + τ²/(τ²+v_i) · (d_i − d̄)
```

- **B1**：`src/source_shot_origin.js` 提供 `shotOriginTables()` / `attachShotOrigin()` /
  `shotOriginAdjustment()`；`src/probability_model.js` 只在 `makeShort` 加一項再 clamp。
  **預設關閉**：`shotOriginAdjustment()` 在 `handler.shotOriginMeasurement` 不存在時回 0，
  而只有 v55 的 input（`reports/ovr-v55-finisher-fix-2025-26/input.mjs`）會掛上這個欄位。
- **B2**：在 v55 的 input 裡用同一條公式、同一個 `shotDelta`、同一個聯盟先驗重算
  `shootingMeasurement.rates`，偽計數 100 → **200**（`rates-reliability.mjs`）。不動凍結的
  `reports/player-impact-v9/input.mjs`。**跑完後證實這一半是空操作**（§6.1）。
- 變體：`B1` / `B2`（歸因）、`B12`（主判定）、`B12_oos`（s_i、d_i 只用 2022-23～2024-25）。

### 2.1 聯盟水準常數 c，以及一個與預先登錄假設**相反**的實測結果

預先登錄寫「模擬普遍餵得比現實少，若不校正會讓全聯盟禁區命中率一起下滑」。校正跑量出來的是
**反的**：

| 量 | 值 |
|---|---|
| 現實聯盟餵球占比（2025-26 非補籃禁區） | **.4398** |
| 模擬聯盟餵球占比（關掉 B1，2025-26 球隊層一顆種子） | **.6286** |
| 模擬聯盟餵球占比（開 B1，同種子） | .6252 |
| B1 自己對餵球占比的影響 | **−0.0034**（可忽略，且方向為負） |
| 基準模擬相對現實的偏差 | **+0.1888** |

模擬是**餵得比現實多**，不是少。這個量測第一次是在開著 B1 的情況下做的，為了排除「B1 把
`usedAssist` 推向 true」這個自我驗證的可能（接球投機率被加了 gap，`best()` 就更容易選它），
另外做了關掉 B1 的基準量測（`fedshare-diagnostic.mjs` / `fedshare-diagnostic.json`）：B1 自己
只動 −0.0034，所以 **+0.189 的偏差是基準模擬本來就有的**。

因此 c 的實際角色跟預先登錄寫的相反：attempt-weighted 平均調整量是 **+0.0329**（模擬餵得多 ⇒
平均吃到正的調整），所以 **c = −0.0329**（`center.json`，2025-26 球隊層、種子 20261012、
1230 場、111339 次非補籃禁區出手），把聯盟平均調整量歸零。c 在任何評估跑之前定下來並凍結，
四季、四個變體共用同一個值。

**這個反向結果不改變修正的方向性**，因為真正的差別項是 (模擬餵球率 − 現實餵球率)：

| 球員 | 現實 s̃ | 模擬餵球率 | D̃ | 每次禁區出手的期望調整 |
|---|---:|---:|---:|---:|
| Karlo Matković | .821 | .775 | .189 | −.042 |
| Jaxson Hayes | .879 | .856 | .195 | −.037 |
| Luka Garza | .806 | .712 | .182 | −.050 |
| Isaiah Stewart | .725 | .746 | .221 | −.028 |
| Rudy Gobert | .850 | .806 | .220 | −.043 |
| Neemias Queta | .851 | .809 | .214 | −.042 |

模擬**沒辦法**餵到極端吃餅長人在現實裡的那個程度（上限約 .86），所以 s̃ 越高的人吃到的懲罰
越大；低 s̃ 的持球創造者則得到補償。這正是任務要的方向，只是機制與預先登錄寫的敘述相反——

B1 本質上是「出手來源」的修正，不會、也不應該因為一個人 RAPM 高就少罰他；這兩人的名次能不能
守住，只能靠他們的禁區出手量占總貢獻的比重，以及其他層面（籃板、守備）的貢獻去抵銷。實際結果
見 §5。

原因查到底了。這套板與球隊層用的機率鏈是：

```
player-impact-v53/model.mjs   (dead-ball pressure)
  -> player-impact-v47/model.mjs  (measured FT)
    -> player-impact-v45/model.mjs  (fine zone plan)
      -> player-impact-v41/model.mjs  (fresh-defense override)
        -> player-impact-v28/model.mjs
          -> src/defense_probability.js -> src/probability_model.js
```

`centeredMake` 住在 `reports/player-impact-v14/model.mjs` 的 `spaceProbability()` 裡，而
v28 之後的這條鏈從頭到尾沒有呼叫 `spaceProbability`——v28 只 import
`defenseProbabilities as baseProbability`，v41 的 `exposureDefenseProbabilities` 覆寫更是直接
用 `baseProbability` ＋ 量測防守 logit ＋ `attributeDelta` 重算 `q.make[z]`。對整條鏈 grep
`\.rates\b` 的結果是空的：

```
$ grep -rn "\.rates\b" reports/player-impact-v{28,41,45,47,53}/*.mjs src/source_fresh_defense.js src/defense_probability.js
(無輸出)
```

所以 `shootingMeasurement.rates` 在這兩個 harness 裡根本不被讀。B2 把 rates 的偽計數從 100
換成 200，寫進了物件，但沒有任何消費者。

這同時推翻預先登錄 §0.3 自己的推論。預先登錄說「正確的槓桿是 rates 本身，不是卡片層的
`k_short`」——在 v12–v14 的量測模型裡這句是對的，但這次用的是 v53 引擎，v41 之後 make 走的是
**卡片屬性曲線 ＋ 量測防守 logit**，`k_short` 與 `rates` 兩邊都不進來，進來的是卡片的
`short` / `long` 屬性。這也正好解釋為什麼 v54（只重建卡片 short/long 的 EB 版本）能把
2025-26 球隊層從 4.556 推到 6.289，而 B2 動不了任何一個數字。

誠實記錄兩件事：

1. B2 那一塊板與 12 個球隊層 run 是浪費掉的一組 5090 算力。
2. 預先登錄 §6 的事前平行性檢查寫的是 `ratesK100MatchesV54`（K=100 要重現 v54）與
   `B12ActuallyChangesBox`（B12 要真的動到 box）。兩個都過了，但兩個都抓不到「B2 單獨無效」
   ——K=100 無效與 K=200 無效會給出同一個「通過」。檢查應該是
   `B2AloneActuallyChangesBox`。這是預先登錄設計上的漏洞，不是執行失誤。

### 6.4 Jalen Smith 被誤傷：逐項歸因

卡片 OVR 是 `predictedPer36` 的單調映射，而
`predictedPer36 = intercept + Σ_j b_j · x_ij`（`x` 是標準化屬性，含位置交互項；
`reports/ovr-calibrated-2025-26/calibrate.py` 的 `design()`）。兩個版本吃同一份
`data/season-league.json`，所以 `attributeMean`、`attributeSD`、`x_ij` 都一樣，於是

```
Δpredicted_i = (intercept_B12 − intercept_v53) + Σ_j (b_j^B12 − b_j^v53) · x_ij
```

是恆等式，可以逐項拆乾淨。`reports/ovr-v55-finisher-fix-2025-26/card-player-decomp.py`
做這件事，輸出 `card/decomp-B12.json`。Jalen Smith（PF，Δpredicted −0.303）的分解：

| `pass` | **−0.205** | −1.02 | 係數升價（+0.110），他 pass 低 → 受害 |
| `rebound×PF` | **−0.189** | +1.36 | PF 的籃板斜率沒跟著升，抵銷掉上面的 +0.226 |
| `pass×PF` | +0.154 | −1.02 | PF 的 pass 斜率部分抵銷 |
| `help` | **−0.148** | +1.17 | 係數降價（−0.142），他協防高 → 受害 |
| `long` | **−0.112** | +0.56 | 係數降價（−0.188） |
| `creation` | +0.110 | −1.15 | 係數降價，他自創低 → 受益 |

關鍵在於這組升降價是**全聯盟共用一組係數**，而 Jalen Smith 的屬性輪廓和 Karlo 幾乎一樣：
高 `rebound`、高 `help`、低 `pass`、中等 `long`。把 Karlo 那組屬性降價，就一定同時打到他。

這個種子數下**本來就測不出來**，不論修正有效或無效都一樣。這是預先登錄選錯驗收統計量，
不是修正失效——同一份資料上，由 40 人與 27 人構成的組級條件 A4a 就乾淨地通過了。

### 7.4 B1 或 B2 對 Karlo／Jalen Smith 有沒有更好？

### 7.5 Jalen Smith 為什麼被誤傷，以及下一步方向（不在本輪實作）

原因在 §6.4 拆乾淨了：傷害不是 B1 的禁區修正造成的（B1 給 Jalen Smith 的每次出手修正是
焦點球員裡最小的一組，他的 `s̃` 只有 0.640），而是**卡片回歸把一整個屬性輪廓降價**：
`help` −0.142、`long` −0.188、`pass` +0.110，全聯盟共用一組係數。Jalen Smith 的屬性輪廓
（高 `rebound`、高 `help`、低 `pass`、中 `long`）和 Karlo 幾乎重合，而卡片回歸的輸入只有
15 個屬性＋身高，看不到任何「這球是誰創造的」訊號，所以沒有任何辦法把他和 Karlo 分開。

三個方向，依「能不能解決根因」排序：

1. **把 `s̃`（或 1 − `s̃`，自創禁區比例）加進卡片回歸的屬性向量。** 最直接對症：
   `reports/ovr-v55-finisher-fix-2025-26/shot-origin.json` 已經有全聯盟 417 人的 `s̃` 與
   EB 後的 `D̃`，照 `scripts/build_season_league.js` 的百分位規則映成 40–99 的第 16 個屬性
   即可。這樣 `help`／`long`／`pass` 不必再去當「吃不吃餅」的代理變數，回歸就能讓
   `s̃ = 0.82` 的 Karlo 掉、`s̃ = 0.64` 的 Jalen Smith 留。注意 `creation`（自創 FGA/36）
   已經是衍生屬性，但它是**全場**自創比例，分不出禁區；Karlo 的 `creation` z 是 −1.17、
   Jalen Smith −1.15，幾乎一樣，所以現有屬性真的沒有這個資訊。
2. **修屬性層本身。** `conclusion.md` §6.3 指出卡片給吃餅長人的 `drive`/`help`/`onBall`/`long`
   百分位比 2K 高 16–46，根因在 `scripts/build_season_league.js` 的百分位建構，而不在定價。
   這一輪刻意沒動（預先登錄 §2 把範圍限定在機率模型），但它才是 Karlo 下修只有 +4 的原因：
   屬性膨脹沒被動到，降價只能壓住一部分。
3. **提高目標裡的 RAPM 權重 α。** `calibrate.py --alpha` 現在是 0.5。提高 α 會直接把
   Jalen Smith（多季 65／單季 23）拉回來、把 Karlo（212／230）壓下去，但代價是卡片愈來愈
   不是「模擬校準」而是「RAPM 複刻」，而且會同時放大 RAPM 自己的替補雜訊。建議當成 1 或 2
   做完之後的敏感度分析，不要當主修正。

## 8. 風險、範圍限制與已知的錯誤預測

### 8.1 預先登錄 §3.1 預測錯方向（已在 §2.1 記錄）

預先登錄寫「模擬普遍餵得比現實少」，實測**正好相反**。`fedshare-diagnostic.json`（B1 關掉的
乾淨基準線）：模擬聯盟餵球占比 **0.6286**，現實 **0.4398**，高估 **+0.189**；B1 自己對餵球
占比的影響只有 −0.0034，所以這不是 B1 造成的假象。修正之所以仍然是對的方向，靠的是差分項
`(模擬餵球率 − 現實 s̃)`：模擬餵不到 0.86 以上，吃餅長人的現實 s̃ 又本來就高，兩者相減後
對他們是負的；對持球創造者則是正的。中心常數 c = −0.0329 讓聯盟平均調整為 0。

### 8.2 舊三季球隊層變差

2022-23 / 2023-24 / 2024-25 的勝場 MAE 都退步（+1.73 / +0.38 / +0.56）。歸因：

- v53/v54 從來沒有在這三季上被調過，這三季的 4.0 ~ 4.8 MAE 是「沒被動過」的基準，不是
  被最佳化過的結果；B1+B2 第一次作用在它們身上。
- 這三季的 B1 分割表是用**各季自己的** play-by-play 重建的，EB 的 τ² 逐季差異很大
  （2022-23 τ²=0.0061、2024-25 τ²=0.0044、2025-26 τ²=0.0014），所以 2022-23 的 D̃ 離散度
  最大、調整幅度最大，退步也最大。
- 2025-26 的淨效率 RMSE 反而改善（2.703 → 2.417），說明這不是單純的「調整越大越糟」。
- 實務結論：**要把 v55 修正 B 當成預設行為之前，應該先補一個逐季的 τ² 下限或共享 τ²**，
  這是下一輪最值得做的一件事，但不在本次預先登錄範圍。

### 8.3 個別球員層的判定本身不可靠

§3.4 已量化：582 人中 99.3% 的板間變化 |z| < 2。任何「某人名次要降 N 名」的驗收條件，在
8 顆種子下都是在測雜訊。要讓這類條件可檢定，種子數需要 32 以上（標準誤 ÷2），而且 v54 基準
板也必須用同樣的種子數重跑——本次沒有做，因為那會改動凍結產物的比較口徑並且大幅超時。

### 8.4 卡片層只能重定價、不能修屬性

§5.5：`help`/`long` 的每 10 點價值被調降 0.14 ~ 0.19，但 Karlo 的屬性膨脹本身（short 98.4、
drive/help/onBall/long 百分位比 2K 高 16–46）是在 `scripts/build_season_league.js` 建的，
不在修正 B 範圍。所以吃餅長人的卡片名次下修有天花板，而且會連帶打到屬性輪廓相同但 RAPM 很好
的球員（Jalen Smith −30 名）。

### 8.5 B1 的分割是硬分割、不是球員層的真實比例

類別層 q_k > 0.5 就整類判為餵球，沒有 tracking 資料可以校正到球員層。這會讓同一類動作裡
「自己創造的那幾球」被誤記為餵球。預先登錄 §1.2 的四季穩定性（禁區差 +.146 ~ +.189）是對
這個分割唯一可得的外部檢驗。
